# 生产复刻与调优（源镜像）

本系统已按生产标准调优，可作为源镜像复刻部署。基准机型 **16GB / 8 线程 / SSD**，所有参数均 env 可覆盖。

## 一、复刻新实例（推荐：从仓库全新部署）

```bash
cp .env.example .env
# 按需修改 CORS_ORIGINS / PUBLIC_WEB_BASE_URL / 域名证书 等
./scripts/bootstrap.sh        # 自动生成本实例独立强密钥(__GEN__) 并渲染 proxysql.cnf
docker compose up -d
```

- `bootstrap.sh` 幂等：仅把 `__GEN__`/占位项替换为随机强密钥，不动已配置的真实密钥。
- 每个复刻实例由此获得**独立的** JWT / 数据库 / Redis / RabbitMQ / ProxySQL 密钥，避免“一处泄密、全线沦陷”。
- `proxysql.cnf` 不再硬编码密码，由 `proxysql.cnf.template` + `.env` 渲染；MySQL 监控用户由 `scripts/mysql-initdb/10-monitor-user.sh` 在首次初始化时创建。

> 若复刻方式是“克隆已运行实例（含数据卷）”，务必在新实例上重新生成密钥（重跑 bootstrap 并轮换在用存储的密码），否则克隆体与源共用密钥。

## 二、已应用的生产调优

### MySQL（docker-compose command + .env）
| 参数 | 值 | 说明 |
|---|---|---|
| innodb_buffer_pool_size | 6G | 约 DB 内存 60-70%（更大内存实例上调）|
| innodb_flush_log_at_trx_commit | 2 | 每秒刷 redo，崩溃最多丢 1 秒日志，换写吞吐 |
| innodb_flush_method | O_DIRECT | 绕开 OS 双缓存 |
| innodb_redo_log_capacity | 2G | 减少 checkpoint 抖动 |
| sync_binlog | 1000 | 保留 binlog 便于主从/PITR |
| innodb_io_capacity / max | 2000 / 4000 | SSD |

### 应用
- `APP_ENV=production / APP_DEBUG=false` —— 关闭 SQL echo。

### Celery worker（防内存膨胀）
- 并发按 8 线程下调：SMS 8 / RESULT 4 / DLR 4 / 通用 4；`max_tasks_per_child=500` 周期回收。

### Redis / RabbitMQ
- Redis `maxmemory 1gb` + `volatile-lru`（只淘汰带 TTL 的缓存键）。
- RabbitMQ `vm_memory_high_watermark=0.2` + `disk_free_limit=1GB`（`docker/rabbitmq/rabbitmq.conf`）。

### sms_logs 分区与保留
- 按 `submit_time` 月度 RANGE 分区；`SMS_LOGS_RETAIN_MONTHS=3`。
- `sms_logs_partition_maintenance_task`（beat 每月 1 日 04:00）自动补建未来月分区 + DROP 超期月（瞬间回收磁盘）。

## 三、容量与扩展提示（日发千万级 = 均值 ~116 条/秒）

- **磁盘是硬约束**：sms_logs ≈ 15–20GB/日 → 450–600GB/月。916GB 盘配合 3 个月保留可稳健；更大量需扩盘或缩短保留。
- 吞吐：均值 116/s 该机调优后可达标，高峰由 RabbitMQ 削峰。
- 横向扩展：DB 独立机、Celery worker 与 Go SMPP 网关多节点（调高对应 `*_CONCURRENCY` / `SMPP_GATEWAY_WORKERS`）。
- 更大机型：上调 `INNODB_BUFFER_POOL_SIZE`、各 `*_WORKER_CONCURRENCY` 即可，无需改代码。
